## 冒頭で示すこと

docs の冒頭では、読み手が文書の位置づけを判断できる情報を置く。

- **目的**：この文書で何を明らかにするのか。
- **背景**：なぜこの文書が必要になったのか。
- **対象範囲**：何を扱うのか。
- **非対象**：何を扱わないのか。
- **想定読者**：誰が読む前提なのか。
- **読み手に求める行動**：理解、レビュー、合意、実装、運用判断など、何をしてほしいのか。
- **ステータス**：草案、レビュー中、合意済み、廃止予定など、現在の状態は何か。

冒頭で詳細に入りすぎない。
読み手は、先に文書の境界と使い道を知る必要がある。

悪い例：

通知機能についてまとめる。

良い例：

この文書は、通知機能の実装方針をレビューするための文書である。
対象読者は、バックエンド実装者、フロントエンド実装者、レビュアーである。
レビューでは、通知生成の責務、既読状態の保存方法、失敗時の扱いを確認する。

## スコープと非対象

対象範囲は、含めるものだけでなく、含めないものも書く。

悪い例：

通知機能を実装する。

良い例：

この文書では、アプリ内通知の生成、保存、取得、既読化を扱う。
メール通知、プッシュ通知、通知文面の AB テストは扱わない。

非対象には理由を添える。
理由がない非対象は、恣意的な除外に見える。

非対象は、意図的にスコープ外とするものだけを書く。
「この文書では触れない詳細」「別文書を参照する内容」は、それだけでは非対象ではない。
別の文書が正本を担う場合は、関連文書や参照先として示す。

良い例：

メール通知は扱わない。
今回の目的は、ユーザーがアプリ内で確認する通知履歴を作ることであり、外部チャネルへの配信は別の配信基盤の設計に依存するためである。

## 文書に書かないもの

docs には、すべての情報を複製しない。

正本が別にある情報は、本文に複製せず、要約と参照にとどめる。
同じ情報が複数箇所にあると、更新漏れによって矛盾が発生する。

別文書を参照するときは、その文書の役割 (正本 / 記録 / 参考) も明記する。
「正本」の語の使い分けは `Spec Workflow Contract` の正本境界「用語規約」に従う。

文書に書かないものの例は次である。

- コードから生成できる詳細な API 一覧。
- 関数単位の説明。
- 実装判断に使わない歴史的経緯。
- 過去の記述の訂正。「当初はこう書いたが誤りだった」「前提が崩れた」は、前の版を知らない読み手には解決できない。現在の事実だけを書く。
- 本文へ添える決定日の注記。「(2026-08-18 決定)」の形で文へ挿し込まない。日付は経緯の一覧か ADR が持つ。
- 後続作業で参照しないファイル名、関数名、識別子。
- 正本が別にある設定値や運用手順の全文コピー。
- 文書の目的に関係しない周辺情報。
- 決定済みでない内容を、確定事項のように見せる図表。

書かないことは、情報を隠すことではない。
正しい場所に置き、必要な場所から参照できるようにすることである。

ただし、参照で済ませてよいかは参照先の寿命で決まる。次節を参照する。

## 参照先の寿命を確認する

「正本があるなら参照にとどめる」は、**参照先が自分と同じかそれより長生きする場合にだけ成り立つ**。

文書には寿命の差がある。

- **永続**: 決定記録 (ADR)、規約、ドメイン知識。決定が覆るまで読まれ続ける。
- **一時**: 個別の開発に紐づく要求文書、設計書、調査メモ。その開発が終われば参照されなくなり、移動や削除もされる。

**永続文書から一時文書を参照してはならない。** 参照先が消えた時点で、永続文書は「なぜそう決めたか」を失う。一時文書から永続文書を参照するのは正しい。

悪い例 (決定記録の中で)：

満たすべき業務ルールは要求文書が正本である。方式選定に効くものだけ再掲する。

良い例 (決定記録の中で)：

満たすべき業務ルールは次のとおりである (要求フェーズで確定。番号は要求時の採番)。

(前提を全件、実体として記載する)

判断の手順は次である。

1. 参照しようとしている文書の寿命を確認する。
2. 参照先が自分より短命なら、参照ではなく**実体を書く**。要約ではなく、その文書だけで判断が再現できる粒度で書く。
3. 同じ寿命か長命なら、参照にとどめてよい。

トレーサビリティのための参照 (Issue 番号、チケット番号) は、寿命に関係なく残してよい。これは情報の複製ではなく所在の記録である。

## 文書分割の粒度

一つの文書に詰め込みすぎない。

次のいずれかに当てはまる場合は、別文書への分割を検討する。

- 対象読者が異なる。
- 読み手に求める行動が異なる。
- 独立して理解できるトピックになっている。
- 更新頻度が異なる。
- 詳細度が大きく異なる。
- 正本にすべき場所が異なる。
- 一つの文書内で Why、What、How が混ざり、流れが追いにくくなっている。

分割した文書は、階層または参照関係でつなぐ。
同じ情報を上下の文書で重複させない。

上位文書は、背景、目的、制約、全体像を担う。
下位文書は、上位文書の文脈を受け取り、より狭い対象の判断、設計、仕様、作業内容を担う。

上位文書の目的は、下位文書の背景になりうる。
上位文書に登場する構成要素は、下位文書の対象範囲になりうる。

## 定義を使用箇所より前に置く

区分、記号、型、分類を導入するときは、**それを使う表や本文より前**に定義を置く。

段落内の論証を一方向に進めるだけでは足りない。節の配置も一方向にする。

よくある失敗は、表の列に区分を入れておきながら、その区分の定義を表より後ろの節に置くことである。読み手は表を読んだ時点で意味が分からず、後ろを探しに行くことになる。書き手は執筆順 (調査してから分類した) のまま並べてしまうため、この順序は起きやすい。

- 表の列に使う区分は、表の直前に定義表を置く。
- 複数の節で使う区分は、最初の使用箇所より前に独立した節を立てる。
- 定義が長くなる場合でも、使用箇所に短い定義を置き、詳細を後ろに回す。逆にはしない。

複数の軸が同時に出るときは、**軸ごとに分けて定義する**。「種別」と「重要度」のように直交する区分を一つの説明にまとめると、どちらの話か読み取れなくなる。

## レビュー可能にする

docs は、レビューできる形で書く。
読み手が賛成、反対、保留、追加確認を返せる状態にする。

レビューしてほしい場合は、次を書く。

- 何を判断してほしいのか。
- どの節を重点的に見てほしいのか。
- どこまでが決定済みなのか。
- 何が未決定なのか。
- 何が今回の対象外なのか。
- いつまでにコメントが必要なのか。

悪い例：

確認お願いします。

良い例：

今回は、通知履歴の保存先、既読状態の持ち方、失敗時の扱いをレビュー対象にする。
UI 文言、メール通知、プッシュ通知は今回の対象外である。
特に、通知履歴を既存 DB に保存する判断に問題がないかを確認してほしい。

## 図表を使う

図表は装飾ではなく、認知負荷を下げるために使う。

図表を使うべき場面は次である。

- コンポーネント間の関係。
- データの流れ。
- 状態遷移。
- 処理の時系列。
- 責務の分界。
- 選択肢の比較。
- 権限や操作範囲の境界。
- 条件と結果の対応関係。
- 文書間の関係。

図表の直後には、その図表から読み取るべきことを一文で書く。
図表に書いてある要素を本文でなぞらない。

## 図の粒度を揃える

同じ対象を、複数の図で重複して説明しない。
図は、文書の抽象度に合わせて描く。

上位の文書では、全体像、外部との関係、主要な構成要素を示す。
下位の文書では、特定の対象の内部構造、処理の流れ、状態遷移、条件分岐を示す。

未確定の論点が残る対象は、確定事項のように図にしない。
推測で描いた図は、読み手に誤った合意を与える。

図を描くときは、次を守る。

- 図の目的を本文で示す。
- 矢印の意味を一貫させる。
- データの流れ、依存方向、呼び出し方向を混同しない。
- 技術名は、読み手が判断できる粒度で具体的に書く。
- 図に出した要素は、本文の責務説明と矛盾させない。
- 同じ対象を別の図で描く場合は、抽象度の違いを明確にする。
