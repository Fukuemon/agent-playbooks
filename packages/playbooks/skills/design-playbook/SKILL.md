# design-playbook

その作業 1 回のための手順を組み、その手順で進める。組んだ手順は保存しない。

## 1. 枠を決める

次の 3 つを書き、利用者に見せる。利用者が離れているときは、書いて進める。

- **終了の条件:** 合否が出る形で書く。「〇〇を呼ぶ箇所が 0 件」「受け入れの条件の各項目が通る」のように書く。「良くする」「4 時間作業する」は終了の条件にならない。
- **範囲:** 作業の単位の数、触るモジュール、作業を止める障害を、数で書く。
- **厳密さ:** 通すチェックと、残す記録で決める。取り消しにくい作業ほど厳密にする。

## 2. 手順を組む

- 作業を、それぞれ単独で取り込んでもビルドとテストが通る単位に分ける。
- うまくいくかが最も分からない単位から並べる。
- 作業より先に、終了の条件を確かめる仕組み（数えるスクリプト、チェック）を作り、作業の前の値を記録する。
- 組んだ手順を、番号付きで todolist に写す。スキル run-playbook の共通の規則に従う。

## 3. 単位ごとに進める

- 1 つの単位を終えるたびに、手順 2 の仕組みで確かめる。判定は「確かめた」「確かめられなかった」「結論が出ない」のどれかにする。結論が出ないものを、確かめたとは数えない。
- サブエージェントに任せた単位は、その報告ではなく、成果物を自分で確かめる。
- 分かれ道の判断を記録する。形は、スキル run-playbook の共通の規則の「判断の記録」に従う。

## 4. 終えて返す

- 終了の条件を、手順 2 の仕組みで確かめる。
- 作業の途中で 2 回した訂正は、スキル run-playbook の `principles/encode-lessons.md` に従って、チェックか仕組みに移すかを判断する。
- 返答に、組んだ手順、終了の条件ごとの結果、判断の記録の場所、決まっていないことを書く。
