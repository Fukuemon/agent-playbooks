# requirements

**担当:** 利用者が実現したいことを、誰の何のためか、どこまで作るか、どうなれば終わりかまで整理し、種別を選んで issue にする。種別が決める時点で、要求をタスクに分ける。  
設計と実装はしない。設計に進むのは feature である。

1. 依頼から、次の 4 つを読み取る。読み取れないものは、推奨の案を添えて利用者に尋ねる。推測で埋めない。
   - 誰が使うか、何に困っているか。
   - 何を作り、何を作らないか。
   - 受け入れの条件。確認できる形で書く。
   - 関係する PRD、Design Doc、context、ADR。
2. 関係する文書と既存の issue を読み、重なる要求と食い違う決定がないかを確認する。食い違いは利用者に示す。
3. 要求の種別を選ぶ。`context/project.yml` の `process.presets` の種別から、依頼に合うものを 1 つ選ぶ。種別ごとの playbook は、スキル run-playbook の「種別から playbook への対応」にある。
   - 合う種別が無いか、2 つの種別にまたがるときは、判断の 3 段の 2 段目の論点として尋ねる。2 つにまたがる依頼は、要求を分ける案を推奨にする。
   - `process.presets` が無ければ、種別を選ばず、`process.defaults` を既定にして、違うものだけを決める。
   - 選んだ種別のプリセットと違う開発プロセスがあれば、それだけを決める。
4. issue の題と本文を下書きする。書き方は、スキル write-issue-pr に従い、要求の起票の雛形があれば使う。種別は雛形の「種別」欄に書き、プリセットと違う点だけを「進め方」欄に書く。
5. 下書きを利用者に見せ、起票してよいかの指示を待つ。
6. 指示を受けて起票する。起票した issue の URL を返す。
7. 種別の `breakdown_at` を読み、下の「タスクに分ける」を行う時点を決める。種別を選ばなかったときは、`process.defaults` の `breakdown_at` を読む。
   - `none` なら、`skip: 分解の時点が none` とする。要求は 1 つの pull request で閉じる。
   - `requirements` なら、ここで行う。
   - それより後の時点（`design` など）なら、ここでは分けず、その時点を返答に書く。スキル run-playbook の「種別から playbook への対応」の、起票した要求の続きを進める playbook が、その時点で行う。

## タスクに分ける

要求の子のタスクを、種別の `tasks` の種類（`design`、`impl`、`verify`、`docs`）ごとに起票する。種別が無ければ、受け入れの条件と決まった設計から、要る種類を選ぶ。書き方と大きさの規則は、スキル write-issue-pr に従う。

1. 受け入れの条件と、決まった設計から、1 つの pull request で閉じられる大きさのタスクを書き出す。
2. 子の数を数える。10 件までなら手順 3 へ進む。10 件を超えるなら、要求を分ける案と、束ねる milestone の案を、論点として尋ねる。
3. `tasks` に `verify` があるか、種別が無く、マージの後にしか確認できない受け入れの条件があれば、その条件を確認する検証のタスクを足す。検証のタスクは playbook verification で進める。
4. タスクの下書きを利用者に見せ、起票してよいかの指示を待つ。事前の権限の範囲にあれば、待たずに進める。
5. 要求の子（sub-issue）としてタスクを起票する。issue の親子は、要求とタスクの 1 段だけにする。

**止まる:** 手順 1 で読み取れない項目が残るとき。手順 3 で種別を尋ねるとき。手順 5 で起票の指示を待つとき。「タスクに分ける」の手順 2 で子が 10 件を超えるときと、手順 4 で起票の指示を待つとき。

**返答に書くこと:** issue の URL か下書き、選んだ種別とプリセットと違う開発プロセス、分解の時点と起票したタスク、利用者に尋ねて決めたこと、決まっていないこと。
