# requirements

**担当:** 利用者が実現したいことを、誰の何のためか、どこまで作るか、どうなれば終わりかまで整理し、issue にする。  
設計と実装はしない。設計に進むのは feature である。

1. 依頼から、次の 4 つを読み取る。読み取れないものは、推奨の案を添えて利用者に尋ねる。推測で埋めない。
   - 誰が使うか、何に困っているか。
   - 何を作り、何を作らないか。
   - 受け入れの条件。確認できる形で書く。
   - 関係する PRD、Design Doc、context、ADR。
2. 関係する文書と既存の issue を読み、重なる要求と食い違う決定がないかを確認する。食い違いは利用者に示す。
3. 行う開発プロセスを選ぶ。`context/project.yml` の `process.defaults` を既定にし、違うものだけを決める。
4. issue の題と本文を下書きする。書き方は、スキル write-issue-pr に従い、要求の起票の雛形があれば使う。
5. 下書きを利用者に見せ、起票してよいかの指示を待つ。
6. 指示を受けて起票する。起票した issue の URL を返す。

**止まる:** 手順 1 で読み取れない項目が残るとき。手順 5 で起票の指示を待つとき。

**返答に書くこと:** issue の URL か下書き、選んだ開発プロセス、利用者に尋ねて決めたこと、決まっていないこと。
