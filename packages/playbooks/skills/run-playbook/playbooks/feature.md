# feature

**担当:** 振る舞いを足すか変える変更の、設計から pull request まで。設計を決め、レビューし、本物で確かめる。  
要求が決まっていなければ、先に requirements を使う。設計の判断が要らない変更は small-change である。

1. 対象の issue を読む。受け入れの条件がなければ、requirements に戻る。
2. spec を置くかを決める。置くのは、設計の論点があるとき、複数のモジュールにまたがるとき、作業が 1 回の会話で終わらないときである。
   - 置くときは `specs/<issue 番号>-<主題>/index.md` を作る。書き方はスキル write-design-docs に従う。
   - 同じディレクトリに `process.yml` を置き、選んだ開発プロセスと進み具合を書く。手順を終えるたびに進み具合を直す。
3. 変更する箇所の今の動きを読む。関係する Design Doc、context、ADR と、コードを読み、変更が触る範囲を書き出す。
4. 設計の案が複数あり、後から変えると高くつくときは、形の違う案を 2〜3 つ比べる。見た目、操作、速さのように、作ってみないと決まらない判断は、prototype で決めてから戻る。決めた案と理由を spec に書く。選択肢を比べて決めた判断は、ADR にする。
5. 骨組みを書く。関数の境界をまたぐ変更では、処理を書く前に、データの形、型、関数のシグネチャ、モジュールの境界を、中身のない本体（未実装の例外を投げるだけ）で書く。骨組みはコミットしてよい。
6. spec を置いたときは、設計と骨組みをスキル review-changes でレビューする。指摘への対応の方針は、利用者と決める。
7. 骨組みに沿って実装する。骨組みにない引数や分岐が要ると分かったら、そのまま足さず、骨組みが誤っていたのかを判断し、誤っていれば手順 4 に戻る。小さな単位ごとにテストかチェックを通してから、次の単位に進む。単位ごとにコミットする。
8. 本物で確かめる。prove-it-works を読む。受け入れの条件の各項目に、確かめた方法と結果を対応づける。
9. 残す設計を、`process.yml` の `reflect_at` の時点で Design Doc、context、ADR に移す。書き方はスキル write-design-docs と write-context に従う。
10. 差分をスキル review-changes でレビューし、指摘を直す。
11. opening-a-pr を行う。

**止まる:** 手順 4 で利用者だけが決められる判断があるとき。手順 6 の指摘への対応の方針。

**返答に書くこと:** 作ったもの、選んだ設計と理由、受け入れの条件ごとの確かめた結果、Design Doc と context と ADR に移したもの、決まっていないこと。
