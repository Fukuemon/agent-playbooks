# feature

**担当:** 振る舞いを足すか変える変更の、設計から pull request まで。設計を決め、レビューし、本物で確認する。  
要求が決まっていなければ、先に requirements を使う。設計の判断が要らない変更は small-change である。

1. 対象の issue を読む。受け入れの条件がなければ、requirements に戻る。
2. spec を置くかを決める。置くのは、設計の論点があるとき、複数のモジュールにまたがるとき、作業が 1 回の会話で終わらないときである。
   - 置くときは `specs/<issue 番号>-<主題>/index.md` を作る。書き方はスキル write-design-docs に従う。
   - 同じディレクトリに `process.yml` を置き、選んだ開発プロセスと進み具合を書く。手順を終えるたびに進み具合を直す。
3. 変更する箇所の今の動きを読む。関係する Design Doc、context、ADR と、コードを読み、変更が触る範囲を書き出す。
4. 設計の案が複数あり、後から変えると高くつくときは、形の違う案を 2〜3 つ比べる。見た目、操作、速さのように、作ってみないと決まらない判断は、prototype で決めてから戻る。決めた案と理由を spec に書く。選択肢を比べて決めた判断は、ADR にする。
   - 分解の時点が `design` なら、設計を決めた後に、requirements の「タスクに分ける」を行う。分解の時点は、要求の種別の `breakdown_at` にあり、種別が無ければ `process.defaults` の `breakdown_at` にある。
   - テストの観点を、スキル design-test-cases で設計する。観点は、受け入れの条件と、手順 3 で書き出した範囲から作る。スキルが無ければ `skip: verification のパッケージが無い` とする。
   - 画面を足すか変えるときは、screen-spec の手順 3 と 4 で画面仕様書を書く。スキル write-screen-spec が無ければ `skip: screens のパッケージが無い` とする。
5. 骨組みを書く。関数の境界をまたぐ変更では、処理を書く前に、データの形、型、関数のシグネチャ、モジュールの境界を、中身のない本体（未実装の例外を投げるだけ）で書く。骨組みはコミットしてよい。
6. spec を置いたときは、設計と骨組みをスキル review-by-viewpoints でレビューする。スキルが無ければ `skip: review のパッケージが無い` とし、spec を自分で読み直す。指摘への対応の方針は、利用者と決める。
7. 骨組みに沿って実装する。骨組みにない引数や分岐が要ると分かったら、そのまま足さず、骨組みが誤っていたのかを判断し、誤っていれば手順 4 に戻る。小さな単位ごとにテストかチェックを通してから、次の単位に進む。単位ごとにコミットする。
   - 画面とコンポーネントのコードは、スキル write-design-system の「画面を作るとき」の手順で書く。スキルが無ければ `skip: design-system のパッケージが無い` とする。
8. 本物で確認する。prove-it-works を読み、そこが挙げる context の手順で動かす。受け入れの条件の各項目に、確認した方法と結果を対応づける。
9. 残す設計を、`process.yml` の `reflect_at` の時点で Design Doc、context、ADR に移す。書き方はスキル write-design-docs と write-context に従う。
10. 差分をスキル review-by-viewpoints でレビューする。スキルが無ければ `skip: review のパッケージが無い` とし、差分を自分で読み直す。判定が「合格」なら手順 11 へ、「要修正」なら直して手順 10 に戻る。3 周しても「要修正」が残れば、残った指摘を論点として尋ねる。
11. opening-a-pr を行う。

**止まる:** 手順 4 で、判断の 3 段の 2 段目の論点に依存する作業しか残らないとき。手順 6 の指摘への対応の方針。手順 10 で、上限に当たったとき。

**返答に書くこと:** 作ったもの、選んだ設計と理由、受け入れの条件ごとの確認の結果、動作確認のエビデンスの場所、Design Doc と context と ADR に移したもの、決まっていないこと。
