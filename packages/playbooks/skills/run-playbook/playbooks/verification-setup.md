# verification-setup

**担当:** リポジトリに、アプリを利用者と同じ方法で動かして確認する手段を作り、アプリの変化に合わせて保つ。ほかの playbook の「本物で確認する」手順は、この手段を使う。  
手段は、利用者のリポジトリだけの知識なので、スキルではなく context とスクリプトに置く。

- 確認の方法の文書: `context/testing/verification.md`。`context/testing.md` からリンクする。
- 機能ごとの確認の方法: `context/testing/verification/<機能>.md`。
- 動かすスクリプト: `scripts/verify/`。

文書の書き方は、スキル write-context に従う。

## 作るとき

1. リポジトリを読んで、次を答える。コードから読めないことだけを利用者に尋ねる。
   - 利用者が触るもの: 画面、CLI、API、ライブラリ。主なものを 1 つ選び、残りを書き留める。
   - 起動の方法: リポジトリに書かれた開発用のコマンド、ポート、環境変数、初期のデータ、認証。
   - 動かす方法: 既にある E2E のテストや操作の仕組みを先に使う。なければ、画面はブラウザの操作、CLI は端末の操作、API は HTTP で動かす。
   - 残せる証拠: スクリーンショット、端末の出力、応答、ログ、終了コード、データの状態。
   - 2 つを同時に動かせるか。動かせないなら、そう書く。
2. リポジトリがそのままでは起動しないときは、先に直すか、何が足りないかを利用者に伝える。
3. `verification.md` に次のセクションを書く。例ではなく、このリポジトリの実際のコマンドと、変わりにくい目印（ARIA のラベル、data 属性、プロンプトの文字列、ルートのパス）で書く。
   - 起動: 起動のコマンドと、準備ができたと分かる合図。止め方。
   - 状態の確認: 動かす価値のある状態か（プロセス、版、ポート、認証）を、何も変えずに確認するコマンド。
   - 操作: 動かし方。
   - 証拠: 何を撮り、どこに残すか。利用者と同じ手順で動かし、テストのための近道を使わない。見た目だけでなく、書かれたファイルやデータも確認する。
   - 後片付け: 自分が起動したものだけを止める。証拠は消さない。
4. 主な機能を 3〜5 つ選び、機能ごとの文書を作る。セクションは、機能の中身、利用者の側からのたどり方、手段での動かし方、注意点にする。
5. スクリプトは `scripts/verify/` に置き、実行できるようにして、呼び方を `verification.md` に書く。
6. 書いた手順を、最初から最後まで 1 回実行する。起動、状態の確認、1 つの機能の操作、証拠の記録、後片付け。後片付けの後も証拠が残ることを確認する。失敗したら直し、毎回後片付けを実行する。実行していない手順は、できたことにしない。

## 保つとき

1. 前回に確認した後の変更を、`git log` で読む。画面、コマンド、ルート、設定の変更を探す。
2. 機能ごとの文書の手順を、本物で動かす。
3. アプリが変わって手順が合わなくなったものは、文書を直す。アプリの不具合で手順が通らないものは、文書を直さず、不具合として利用者に伝える。退行を文書の書き換えで隠さない。
4. 新しい機能があれば、機能ごとの文書を足す。

**止まる:** 起動に必要な秘密情報や外部のサービスが手元にないとき。

**返答に書くこと:** 作るか直した文書とスクリプト、最初から最後まで実行した結果と証拠の場所、動かせなかった機能とその理由。
