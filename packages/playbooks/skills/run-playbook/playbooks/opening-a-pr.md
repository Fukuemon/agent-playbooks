# opening-a-pr

**担当:** 終えた変更を、すぐレビューできる pull request にする。ほかの playbook の最後に呼ぶ。  
pull request の指摘への対応は、pr-follow-up が行う。

1. 作業は、統合ブランチから切った作業用のブランチで行う。保護するブランチに直接コミットしない。ブランチの名前は CONTRIBUTING.md に従う。
2. 変更を関心ごとのコミットに分ける。分け方とメッセージは、スキル write-commit に従う。
   - コミットのフックが失敗したら、原因を直してからコミットし直す。フックを飛ばさない。
   - 生成物の差分を確認するフックがある repo では、生成先のファイルを含むコミットを先に作る。
3. push の前に、CONTRIBUTING.md の「コミットするとき」と CI が実行するチェックを、手元で実行する。
4. 題と本文を下書きする。書き方は、スキル write-issue-pr に従う。本文には、確認したことと確認していないこと、決まっていないことを書く。
5. push と pull request の作成の前に、利用者の指示を待つ。スキル run-playbook の規則の索引の「事前の権限」の範囲にあれば、待たずに進める。
6. 指示を受けて push し、pull request を作る。下書き（Draft）で作るかは、CONTRIBUTING.md の取り決めに従う。取り決めがなければ、レビューできる状態で作る。
7. 機能の pull request では、動作確認のエビデンスを載せる。機能の pull request は、振る舞いを足すか変えるものである。文書だけの pull request と依存の更新は、対象外にする。利用者の `context/testing/evidence.md` の Evidence Scope に範囲があれば、それを読む。
   - スキル capture-pull-request の手順で、観点を設計し、撮って、pull request のスレッドに投稿する。
   - 観点の承認と、投稿したスレッドの確認は、判断の 3 段の 2 段目の待ちとして扱う。待つ間は、ほかの作業を進める。利用者がスレッドを確認したら、スキルの「9. 本文に動画を並べる」を行う。
   - 利用者がスレッドを確認するまで、pull request をマージしない。
   - スキルが無ければ `skip: verification のパッケージが無い` とし、「確認したこと」に「未実施」と理由を書く。
8. CI の結果を待つ。失敗したら pr-follow-up を行う。

**止まる:** 手順 5 で、事前の権限がなく、push と作成の指示を待つとき。手順 7 の確認の待ちでは止まらず、ほかの作業を進める。

**返答に書くこと:** pull request の URL、コミットの一覧、CI の結果、エビデンスのスレッドの URL と利用者の確認の状態。
