# verification

**担当:** 要求の受け入れの条件を、子の実装の pull request がマージされた後に確認する。検証の設計を書き、エビデンスを撮って検証の pull request に載せ、検証の issue と親の要求を閉じる。  
受け入れの条件を確認する検証の issue（`type:verify`）から始める。1 つの pull request の動作確認は、opening-a-pr の中で行う。

1. 検証の issue と親の要求を読み、受け入れの条件を書き出す。親の要求の子の実装の pull request を集め、それぞれの差分を読む。マージされていない子があれば、その子と、それに依存する受け入れの条件を返答に書く。
2. 改修の内容と影響の範囲を洗い出し、手順 3 の入力として書く。
   - 変わった振る舞い
   - 変わったファイルとモジュール
   - 呼び出し元と依存先
   - 画面、API、データ
3. 検証の設計を、スキル design-test-cases の形（EARS の要件）で書く。観点は、受け入れの条件と手順 2 の結果から作り、関心ごと（画面ごと、機能ごと、権限、データ、回帰）にセクションを分ける。受け入れの条件ごとに、確認する観点を対応づける。
   - 置き場は、`context/testing/evidence.md` の Verification Scenarios にある、検証のシナリオのファイルの置き場にする。書かれていなければ、判断の 3 段の 2 段目の論点として尋ねる。
   - スキル design-test-cases が無ければ、`skip: verification のパッケージが無い` とし、手順 3〜5 の代わりに、受け入れの条件ごとの確認の結果を検証の issue に書いて、手順 6 に進む。
4. 検証の設計のシナリオから、スキル write-verification-spec で spec を書き、スキル run-verification-scenarios で撮る。
   - スキル write-verification-spec が無いか、e2e の kit が入っていなければ、`skip: e2e のパッケージが無い` とする。撮らなかった観点は、返答と検証の pull request の「確認したこと」に「未実施」と理由を付けて書く。
   - 撮ったエビデンスを、run-verification-scenarios の「確認する」で見る。判定が「揃っている」なら手順 5 へ、「撮り直す」なら spec を直して手順 4 に戻る。3 周しても「撮り直す」が残れば、残った観点を論点として尋ねる。
   - シナリオと食い違ったら、spec で合わせず、run-verification-scenarios の「シナリオと食い違ったら」のとおり利用者に示す。
5. 検証の設計と spec を持つ検証の pull request を、opening-a-pr で作る。エビデンスは、スキル capture-pull-request の「7. 投稿する」で pull request のスレッドに載せ、利用者がスレッドを確認してから「9. 本文に動画を並べる」で本文に並べる。
6. 検証の pull request のマージで、検証の issue を閉じる。親の要求の子が全て閉じていれば、確認した受け入れの条件にチェックを付け、親の要求を閉じる。確認できない条件が残れば、親を閉じず、残った条件をコメントに書く。書き方は、スキル write-issue-pr に従う。issue の書き換えは、事前の権限の範囲にあるときだけ行う。

**止まる:** 手順 3 で、検証の設計の置き場が決まっていないとき。手順 4 で、撮り直しの上限に当たったとき。手順 5 で、利用者がスレッドを確認するのを待つとき。手順 6 で、issue の書き換えが事前の権限の範囲に無いとき。

**返答に書くこと:** 受け入れの条件ごとの観点と確認の結果、改修の内容と影響の範囲、検証の pull request の URL とエビデンスの場所。未実施の観点と理由、閉じた issue と開いたままの条件。
