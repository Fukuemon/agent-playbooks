# pr-follow-up

**担当:** pull request を、マージできる状態まで運ぶ。レビューの指摘、CI の失敗、マージ先との競合に対応する。  
マージはしない。マージは利用者が決めるか、スキル run-session の coordinate-workers が事前の権限の範囲で行う。

1. pull request の状態を読む。CI の結果、レビューとコメント（自動のレビューを含む）、競合の有無、マージ先のブランチ。
2. CI の失敗を、ログから原因ごとに分ける。原因を分けずに CI を再実行しない。
   - 今回の変更が原因のもの: 直す。
   - マージ先でも同じように失敗するもの: 今回の範囲の外として返答に書く。
   - 環境の一時的な失敗: 根拠を示してから再実行する。
3. レビューの指摘を 1 件ずつ読み、次の 3 つに分ける。自動のレビューも、指摘ごとに中身で判断する。
   - 直す: 指摘が正しく、この pull request の範囲にある。
   - 直さない: 指摘が誤っているか、範囲の外にある。理由を具体的に書く。
   - 尋ねる: 判断の 3 段の 2 段目の論点を含む。答えを待つ間に、ほかの指摘を進める。
4. 直すものを直し、関心ごとにコミットする。指摘の原因が、配布されたパッケージや外部のツールにあるときは、ここでは直さず、記録して返答に書く。
5. CONTRIBUTING.md と CI のチェックを手元で実行してから push する。エビデンスを載せた pull request で振る舞いを変える push をしたら、スキル capture-pull-request の「push があったとき」を行う。
6. CI の結果を待つ。判定が「通った」で直すものが残らなければ終える。「要修正」（CI の失敗か、直す指摘が残る）なら手順 1 に戻る。3 周しても「要修正」が残れば、残った失敗と指摘を論点として尋ねる。
   - エビデンスのスレッドを投稿した pull request で、利用者がスレッドを確認していなければ、マージできる状態としない。確認を待つ間は、ほかの作業を進める。エビデンスの段を飛ばした pull request は、この待ちの対象外である。

**止まる:** 手順 3 で尋ねるものがあるとき。手順 6 で、上限に当たったとき。push の前に、利用者の指示も事前の権限もないとき。

**返答に書くこと:** 指摘ごとの扱い（直した、直さない理由、尋ねること）、CI の結果、エビデンスの確認の状態、マージできる状態か。
