# pr-follow-up

**担当:** pull request を、取り込める状態まで運ぶ。レビューの指摘、CI の失敗、取り込み先との競合に対応する。  
取り込みはしない。取り込みは利用者が決めるか、coordinate-workers が事前の権限の範囲で行う。

1. pull request の状態を読む。CI の結果、レビューとコメント（自動のレビューを含む）、競合の有無、取り込み先のブランチ。
2. CI の失敗を、ログから原因ごとに分ける。原因を分けずに CI を再実行しない。
   - 今回の変更が原因のもの: 直す。
   - 取り込み先でも同じように失敗するもの: 今回の範囲の外として返答に書く。
   - 環境の一時的な失敗: 根拠を示してから再実行する。
3. レビューの指摘を 1 件ずつ読み、次の 3 つに分ける。自動のレビューも、指摘ごとに中身で判断する。
   - 直す: 指摘が正しく、この pull request の範囲にある。
   - 直さない: 指摘が誤っているか、範囲の外にある。理由を具体的に書く。
   - 尋ねる: 利用者だけが決められる判断を含む。
4. 直すものを直し、関心ごとにコミットする。指摘の原因が、配布されたパッケージや外部のツールにあるときは、ここでは直さず、記録して返答に書く。
5. CONTRIBUTING.md と CI のチェックを手元で実行してから push する。
6. CI の結果を待ち、手順 1 に戻る。CI が通り、直すものが残らなくなったら終える。

**止まる:** 手順 3 で尋ねるものがあるとき。push の前に、利用者の指示も事前の権限もないとき。

**返答に書くこと:** 指摘ごとの扱い（直した、直さない理由、尋ねること）、CI の結果、取り込める状態か。
