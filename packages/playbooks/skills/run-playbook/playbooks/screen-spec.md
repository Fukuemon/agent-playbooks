# screen-spec

**担当:** 画面仕様書（画面ごとの文書と操作できるモック）を、実装より先に書くか、既にある実装と読み合わせる。実装はしない。  
画面を実装する作業は feature である。feature の中で画面仕様書を書くときも、この playbook の手順 3 と 4 を使う。

1. 対象の要求の issue と、関係する PRD、Design Doc を読む。要求が決まっていなければ、requirements に戻る。
   - スキル write-screen-spec が無ければ、`skip: screens のパッケージが無い` とし、作業を進めずに返答に書く。
2. 依頼を、新しい画面を書くか、読み合わせるかに分ける。どちらの作業も、スキル write-screen-spec の規約の読み方に従う。
3. 新しい画面を書くときは、write-screen-spec の「新しい画面を書く」の手順で書く。
4. write-screen-spec の「確認する」を行う。判定が「違反なし」なら手順 5 へ、「違反あり」なら直して手順 4 に戻る。3 周しても違反が残れば、残った違反を論点として尋ねる。ブラウザを使えないときは、ブラウザでの確認を「未確認」として返答に書く。
5. 画面の実装があれば、write-screen-spec の「仕様と実装を読み合わせる」を行う。食い違いごとに、直す先（仕様書、実装、両方）を論点として尋ねる。仕様書を直すと決まったら手順 3 の書き方で直して手順 4 に戻り、実装を直すと決まったら別の作業（feature か bug-fix）に分ける。
6. opening-a-pr を行う。

**止まる:** 手順 4 で、上限に当たったとき。手順 5 で、直す先の答えを待つとき。

**返答に書くこと:** 書いたか直した画面と状態、確認の結果と未確認のもの、読み合わせの食い違いと決まった直す先、決まっていないこと。
