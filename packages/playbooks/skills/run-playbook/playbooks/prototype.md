# prototype

**担当:** 設計の判断を、使い捨ての実装で安く決める。成果物は判断と、使い捨ての実装であり、出荷するコードではない。本番の実装は feature が行う。  
この playbook だけは、smallest-change と、テストや品質の基準が逆になる。速さを優先し、コードの質は問わない。厳密さは、正しい案を安く選ぶことに使う。

1. 決めることを 1 つの問いに絞る。どの配置か、どの操作か、どの方式か、どのくらいの速さか。決めることがなければ、prototype ではない。feature に戻る。
2. 案の幅が広いときは、既存の例や先行の事例を集め、方向を利用者と決めてから作る。方向が決まっていれば `skip: <理由>` にする。
3. 本番のコードと分けて、リポジトリの `.ai-out/` の下の作業用のディレクトリに作る。見た目の判断は、描けるいちばん軽い手段で作る。振る舞いや速さの判断は、問いを試す最小のスクリプトで作る。本番のフレームワーク、テスト、抽象化は使わない。
4. 案は 2〜3 つ作る。同じ形の言い換えは数えない。見た目の案は、1 つの画面で切り替えて比べられるようにし、各案に名前を付ける。
5. 本物で観察する。見た目はスクリーンショットを撮り、操作して確認する。振る舞いや速さは、出力、時間、ログを記録する。ここでは観察が確認の方法であり、テストは書かない。
6. 案、根拠（スクリーンショットや記録）、強みと弱み、推奨を利用者に見せる。決まった方向は feature に渡す。

**止まる:** 手順 2 で方向を決めるとき。手順 6 で、どの案にするかを利用者が決めるとき。

**返答に書くこと:** 試した案、根拠、強みと弱み、推奨、使い捨ての実装の場所。使い捨てであることを書く。
