# refactoring

**担当:** 振る舞いを保ったまま、構造を変える。振る舞いを足すのは feature、直すのは bug-fix である。  
整理の途中で足りない機能や不具合が見つかったら、別の作業に分け、構造の変更を先に出す。多くの箇所にまたがる整理は、スキル design-playbook で手順を組む。

1. 今の振る舞いを先に固定する。変える範囲の振る舞いを読み、今の出力を記録するテスト、スナップショット、比較のスクリプトを書く。テストがない範囲は、固定してから構造に触る。型のチェックと lint は、振る舞いの固定にならない。
2. 目指す形を書く。今から作るとしたら、モジュールの分け方、型、呼び出しの関係がどうなるか。整理で分岐や無効な状態が減らないなら、目指す形を見直す。
3. 足す前に消す。使われないコード、呼び出し元が 1 つしかない包み、重なった検証を先に消す。smallest-change を読む。
4. 振る舞いを保つ小さな歩幅で移す。歩幅ごとに、手順 1 の固定が通ることを確かめる。API の形を変えるときは、呼び出し元をすべて移し、同じ変更で古いものを消す。名前の変更は、文字列、文書、コメントの中の参照も確かめる。
5. 振る舞いが変わっていないことを、本物で確かめる。prove-it-works を読む。大きな整理では、変更の前後の出力を比べるスクリプトを使う。
6. 残す価値を確かめる。読み手がたどる層と覚える状態が減っていなければ、戻す。
7. コミットは、消す変更、形を変える変更、残りの整理の順に並べる。opening-a-pr を行う。

**返答に書くこと:** 変えた構造、固定に使ったもの、振る舞いが変わらないことの根拠、出したものと戻したもの。振る舞いの変更はない、と書く。
