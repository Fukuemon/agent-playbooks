# design-system

**担当:** デザインシステムを導入するか、トークン、コンポーネント、原則を足すか変える。トークン、デザインシステムの文書、カタログを同じ変更で直し、チェックを通す。  
デザインシステムに沿って画面を実装する作業は feature である。feature の中でデザインシステムに足すものが要ると分かったら、この playbook で先に足す。

1. 依頼を、導入か、足すか変えるかに分ける。`context/codebase.md` の Placement Rules に、デザインシステムの文書の場所が書かれていなければ導入として扱う。
   - スキル setup-design-system と write-design-system が無ければ、`skip: design-system のパッケージが無い` とし、作業を進めずに返答に書く。
2. 導入のときは、スキル setup-design-system の手順で進め、手順 6 に進む。元にする公開のデザインシステム、トークンの置き場、接頭辞は、スキルの「尋ねる」のとおり利用者に尋ねる。
3. 足すか変えるときは、DESIGN.md と、トークン、コンポーネントとパターン、カタログの 3 つの文書を読む。書き方はスキル write-design-system に従う。
4. 新しい操作の UI を足すときは、write-design-system の「新しい操作の UI を足すとき」のとおり、使う人が慣れた既存のプロダクトの形を調べて示し、カタログに操作できる例を置いて利用者に触ってもらう。形は利用者が決める。
5. トークン、デザインシステムの文書、カタログのページを、同じ変更で直す。
6. DESIGN.md の「流すコマンド」か、CONTRIBUTING.md の「デザインシステムを直すとき」にあるチェックを流す。判定が「通った」なら手順 7 へ、「通らない」なら直して手順 6 に戻る。直す回数は DESIGN.md の決めに従い、決めが無ければ 2 回までにする。上限に当たるか、違反の数が減らなければ、通らない変更をコミットせずに、残った原則の ID を論点として尋ねる。
   - 直すのに新しい判断（基準を下げる、トークンを足す、コンポーネントを足す）が要るときも、論点として尋ねる。基準を下げて通さない。
7. 差分をスキル review-by-viewpoints でレビューし、指摘を直す。スキルが無ければ `skip: review のパッケージが無い` とし、差分を自分で読み直してから進む。
8. opening-a-pr を行う。報告は、write-design-system の原則の ID ごとの 5 つの状態で、pull request の「確認したこと」に書く。

**止まる:** 手順 2 と 4 で、利用者の答えを待つとき。手順 6 で、上限に当たったときと、新しい判断が要るとき。

**返答に書くこと:** 導入したか足したか変えたもの、直したトークンと文書とカタログのページ、原則の ID ごとの状態、利用者が決めたこと、決まっていないこと。
