# playbook

依頼を受けたら、下の索引から playbook を 1 つ選び、`playbooks/<名前>.md` を開いて、その手順で進める。  
利用者が playbook の名前を添えたときは、その playbook を使う。

## 選び方

- 索引のどれかに当てはまる作業は、その playbook を使う。
- どれにも当てはまらない作業、多くの箇所にまたがる作業、利用者が離れている間に進める作業は、スキル design-playbook で手順を組む。
- 1 つの依頼が 2 つの playbook にまたがるときは、先に行う方を選び、終えてから次を選び直す。調査の結果、コードを変える必要が分かったときが例である。

## 索引

- **requirements:** 実現したいことを整理して、issue にする。まだ作るものが決まっていない依頼。
- **feature:** 振る舞いを足すか変える。設計の判断が要る変更。
- **bug-fix:** 報告された不具合を再現し、原因を突き止めて直す。
- **small-change:** 設計の判断が要らない変更。誤記の修正、設定の値の変更、依存の更新、文書の直し。
- **investigation:** コードを変えずに問いに答える。どう動くか、なぜこうなっているか、どちらを選ぶべきか。
- **opening-a-pr:** 変更を pull request にする。ほかの playbook の最後に呼ぶ。
- **pr-follow-up:** pull request のレビューの指摘と、CI の失敗に対応する。

## 共通の規則

### todolist

- playbook を開いたら、その手順をそのまま todolist の先頭に写す。作業に固有の項目は、その後ろに足す。
- 行わない手順も消さず、`skip: <理由>` を付けて残す。
- 手順を終えるたびに、todolist を更新する。

### 作業の前に読むもの

- リポジトリの `AGENTS.md` と `context/index.md` を読み、作業に関係する context を開く。
- 利用者のリポジトリの取り決めと playbook が食い違ったら、リポジトリの取り決めに従い、食い違いを返答に書く。

### 止まって尋ねる場面

- 元に戻せる作業は、尋ねずに進めて、結果を見せる。
- 実行すれば分かる事実（動き、出力、性能）は、尋ねずに確かめる。
- 次の操作の前では止まり、利用者の明示の指示を待つ。
  - 共有のブランチへの push、pull request の取り込み、デプロイ
  - データの削除と、取り消せない変更
  - 外部のサービスへの送信。issue と pull request の作成と書き換えを含む
- 利用者だけが決められる判断（製品の方針、範囲、優先順位）は、推奨の案を添えて尋ねる。

### principle

手順の途中で次の場面に当たったら、対応する principle のスキルを全文読んでから判断する。  
返答には、読んだ principle と、それで変えた判断を書く。

- **principle-prove-it-works:** 作業を終えたと言う前。
- **principle-fix-root-causes:** 不具合や失敗の原因を探すとき。症状を消す修正を足したくなったとき。
- **principle-smallest-change:** 変更の大きさを決めるとき。抽象化や層を足したくなったとき。
- **principle-encode-lessons:** 同じ訂正や指示を 2 回目に書いたとき。

### サブエージェント

- 広い調査、レビュー、独立した確かめは、サブエージェントに任せる。依頼には、何を返してほしいかを書く。
- サブエージェントが返した結論のうち、返答に使う部分は自分で確かめる。
- サブエージェントの数は、作業に要る分だけにする。1 つで足りる作業を分けない。

### 返答

- 最初に、何が終わったか、または問いへの答えを書く。
- playbook の「返答に書くこと」を必ず含める。
- 確かめたことと、確かめていないことを分けて書く。確かめていないことは「未確認」と書く。
- 取り消せない操作の前で止まったときは、次に利用者がする操作を 1 つ書く。

### skill と playbook の誤り

作業の途中で playbook やスキルの誤りに気づいたら、回避して先へ進めない。誤りを返答に書き、別の pull request で直す。
